# nanocode-machines-web

A template for a nanocode agent that pays for its own model and tools from the visitor's Tempo Wallet. It is the browser counterpart of gakonst/nanocode-machines, whose `nanocode-mpp` CLI pays per request over MPP sessions, and it serves nanocode.xyz/machines/. It is a Vite and React app: by default the agent, its payments and its wallet connection all run in the visitor's browser, and no server holds keys. Once logged in, the page hands the access key to this site's Worker by default (`/local` opts out and is remembered, `/cloud` opts back in), which runs the same agent durably in a Durable Object, with subagents, and pays from that key while the tab is closed. The Worker also serves the static build and relays Tempo Wallet's device-code requests for logins inside X's player.

- `src/agent.ts` runs the nanocode-ts build-de5fd83 WASM module (`nanocode-ts`, `nanocode-ts/nanocode_wasm.wasm`) with an in-memory `@sqlite.org/sqlite-wasm` database, as nanocode.xyz's home page does (tempoxyz/nanocode-site `src/demo/Agent.ts`). The session is Codex `gpt-6-luna` at low effort against `https://openai.mpp.tempo.xyz/v1` with subagents enabled, and the SDK's `dispatch` sends each model request through the payment client unchanged.
- `src/machines.ts` holds the instructions and the suggested prompts, and `src/services.ts` the services and request shapes of the nanocode-mpp storm recording (rpc, openrouter, kicksdb, storage, firecrawl, Microsoft and ElevenLabs speech, fal, goflightlabs) plus the Tempo gateway, shared with the Worker's instructions. The agent has no host tools: it runs in Code Mode (`code_mode: true` with nanocode-ts's `LocalHand`, whose `fetch` is `src/payments.ts`'s mppx fetch), so every `fetch` in an `exec` script pays any MPP service it reaches and the spend panel attributes it per origin. The instructions tell the model to read back only what it needs, because the visitor pays for every token. Before 2026-10-22 its one host tool was `pay`, which reached only `https://<name>.mpp.tempo.xyz`; scripts may now pay any MPP service that allows the page's origin, still bounded by the key's allowance and scopes.
- Tempo's MPP proxies allow browsers. On 2026-10-21 each `*.mpp.tempo.xyz` origin the tool uses answered a preflight from https://nanocode.xyz with `access-control-allow-origin: *`, allowed `authorization`, `content-type`, `payment-session` and `accept-payment`, and exposed `WWW-Authenticate` and `Payment-Receipt`. https://rpc.tempo.xyz allows any origin too. https://mpp.dev/api/services sends no CORS headers, so the service list lives in the instructions.
- `src/wallet.ts` connects Tempo Wallet with the Tempo Accounts SDK (`accounts` 0.21.0, `tempoWallet` with the SDK's default mount, an overlay iframe where the browser supports one and a popup otherwise). The provider is created with `mpp: false`. By default `Provider.create` replaces `globalThis.fetch` with its own mppx client, which pays a 402 by asking Tempo Wallet to sign with the account itself. On 2026-10-21, the first deploy's payment requests went through that polyfill, so Tempo Wallet prompted outside any click and the payments failed as "user rejected the request". `src/payments.ts` also keeps the native `fetch` it found at load. The page generates a secp256k1 access key and asks `wallet_connect` to authorize it (`authorizeAccessKey`), as tempoxyz/xframes builds its services keys (`servicesPolicy` and `keyRequest` in its `src/tempo.ts`), with MACH and one fee token:
  - limits of `allowance` (2 MACH) and `feeAllowance` (0.1 USDC.e), and an expiry a day out;
  - scopes for MACH `transferWithMemo`, MACH `approve` to the swapper and the swapper's `swapTo` (machine-token charges), and the TIP-1034 escrow's `open`, `topUp`, `requestClose` and `withdraw`.

  The key, its account and the returned `keyAuthorization` stay in localStorage under `nanocode.machines.wallet` until the key expires or the visitor logs out, so a script on the page could spend at most what is left of the allowance. `restore` drops a stored key without a USDC.e limit, which builds before 2026-10-21's second deploy approved.
- `publish` puts the key on chain before anything pays with it. It sends one transaction that the key signs and that carries its key authorization: the activation call xframes' `activate` sends, MACH `approve(swapper, 0)`, with its fee paid in USDC.e from the visitor's account. That fee counts against the key's USDC.e limit, because Tempo charges an access key's fees to its limit in the fee token.
  - Publishing first is required: the MPP proxies sponsor channel opens, and mppx's fee-payer policy refuses sponsored transactions that carry a key authorization (`allowKeyAuthorization`, off by default). On 2026-10-21 the first paid request with an unpublished key failed with "fee-sponsored transaction keyAuthorization is not allowed".
  - MACH is not a fee token, so the account needs a little USDC.e: that day the RPC quoted the publication's fee as 1,169 atomics (0.001169 USDC.e).
  - Tempo Wallet's MACH checkout opens with `Mach.fund`, and `wallet_revokeAccessKey` revokes the key.
- `src/payments.ts` pays with mppx 0.13.6, xframes' version. It ranks challenges as xframes' `payer` does: MACH sessions first, then machine-token charges, then MACH charges. Channels live in localStorage per key, so a reload reuses them.
  - The proxies send no `suggestedDeposit`, so mppx would open each channel with one request's price: on 2026-10-21 the first Luna request's open asked for 289 atomics. Every request therefore passes `context.depositRaw` for a 0.05 MACH opening deposit. Top-ups are also 0.05 MACH, and `maxDeposit` caps a channel at 0.5 MACH.
  - Deposits count against the key's limit. Nothing in the page closes channels.
- `src/Terminal.tsx` is the chat. It guides the visitor through logging in with slash commands, as `nanocode-mpp` asks for `tempo wallet login`, and typing `/` lists them:
  - `/login` approves a key in Tempo Wallet, or reuses an approved one, then publishes it and reports the MACH balance;
  - `/wallet` reads the balances and what the key may still spend;
  - `/fund` opens MACH checkout;
  - `/logout` revokes the key in Tempo Wallet and forgets it, and says so when the wallet did not revoke it;
  - `/help` lists the commands.

  Prompts before a login answer with the next step, and payment failures name their fix (`explain` in `src/machines.ts`).
- The page is an xframe, as nanocode.xyz's home page and the Vercel and Cloudflare demos are:
  - **Tags:** its X card is a player card, with `twitter:player` https://nanocode.xyz/machines/ (the page itself) at 480×480, `twitter:site` @nanocodexyz and `twitter:image` https://nanocode.xyz/player/machines.jpg, which tempoxyz/nanocode-site renders from its `Head.players`.
  - **Frame mode:** `public/frame.js`, a head script, marks a framed document `data-xframe` before the body renders. It is a file and not inline because X showed no player card for pages whose HTML held `self !== top`. Under that attribute `.chat` covers the page and fills the frame, and a `nanocode.xyz →` link ends the status line.
  - **Sandbox:** X's player sandboxes the page without `allow-forms`, `allow-top-navigation` or `allow-popups-to-escape-sandbox`, so the composer is not a form and links open new tabs.
  - **Login:** Tempo Wallet cannot run in X's player, because its overlay iframe gets no passkey permission and a popup inherits the sandbox. A framed page therefore logs in with the Accounts SDK's device-code adapter (`accounts/deviceCode`): `/login` shows Tempo Wallet's verification link and code above the composer, and the visitor approves in a new tab or on a phone while the page polls. Tempo Wallet's `/api/auth/device` allows only its own origin in CORS, so the adapter's `fetch` sends `register` and `token` to `api/device/*` on this origin, and `src/worker.ts` forwards those two POSTs unchanged.
  - **Links:** a tab that a link in X's player opens keeps the player's sandbox, so Tempo Wallet's pages cannot submit their forms there. On 2026-10-21 in headless Chrome, inside an iframe with X's sandbox, a plain click on the device link opened Tempo Wallet's sign-in in a tab that blocked its `Create account` submit ("Blocked form submission … the 'allow-forms' permission is not set"), and a ⌘-click opened it in a normal tab. When `sandboxed` finds that the frame cannot submit a form, a plain mouse click on a Tempo Wallet link stays in the page and asks for a ⌘-click (Ctrl-click on Windows) or a phone, as xframes' connect page does. A tap or a modified click opens the link.
  - **Funding:** `/fund` in a frame shows the Accounts SDK's `Mach.getFundingUrl` checkout link. That day a device-code `wallet_deposit` answered a browser not signed in to Tempo Wallet with "No account connected" and only a Close button, while the checkout link opens Tempo Wallet's sign-in.
  - **Checked on 2026-10-21:** in a 480×480 iframe with X's sandbox, under local `wrangler dev`, `/login` showed the link and code. Approving a throwaway account in another tab, with a virtual passkey, gave the frame its key, and the page then tried to publish it.
- `src/Spend.tsx` is the spend panel of the nanocode-mpp TUI. Its title reads `⚡ <total> MACH streamed · <n> paid calls · <n> services · <rate> MACH/min`. Each service has a row with a live `●`, a 30-second sparkline, its spend and its call count. `payments.ts` takes spend from receipts:
  - session receipts come from `Payment-Receipt` headers and from the `payment-receipt` events of metered streams, which it reads as the stream passes through unchanged. Each is charged as the rise in its channel's cumulative `spent` since the last receipt this browser saw, which is kept in localStorage;
  - charges are taken from their challenge's amount on mppx's `payment.response` event.
- The page copies nanocode.xyz's design: `src/style.css` is gakonst/nanocode-vercel-durable's `app/globals.css`, and `src/Reply.tsx`, `src/fences.ts`, `src/highlight.ts` and `src/theme.ts` are its reply and code-highlighting files. `index.html` carries nanocode.xyz's numbered navigation with absolute links and this demo current, so copy navigation changes here as nanocode-vercel-durable and nanocode-cloudflare-durable do. Under the title `src/App.tsx` carries the switch between the Cloudflare, Tempo and Vercel demos that nanocode.xyz's home page shows (the site's `Nav.demos`), with this demo current, and `src/style.css` its rules from nanocode-vercel-durable's `app/globals.css`. Its Open Graph card is https://nanocode.xyz/og/machines.png, which tempoxyz/nanocode-site renders from its `Head.demos`. `Reply` renders Markdown images, which fal's results become.
- `/cloud` runs the agent durably in this site's Worker instead of the tab (`worker/`). The page sends its access key to `POST v1/keys`, and from then on its turns go to `sessions/<session>/turns` and it follows `sessions/<session>/events` (`src/cloud.ts`). A turn keeps running when the tab closes. The page keeps its transcript in localStorage (`nanocode.machines.entries`, the last 300 entries), so a reload shows the conversation and reconnects to an open turn from its saved cursor. `/clear` starts a new session. In the cloud the spend panel is the same `Spend`, fed by `Cloud.meter`, which polls `v1/me` every second for the `Wallet`'s per-host spend (from receipts) and request counts and turns each rise into a charge for the sparkline. `/local` goes back to the tab, and `/logout` also forgets the cloud token. The Worker is gakonst/nanocode-cloudflare-durable's `createNanocode` (sessions in Durable Objects, durable turns, `subagents: true`, hands), pinned by commit:
  - `POST /v1/keys {address, key_type: secp256k1 | p256, private_key}` derives the key's address and checks with `accessKey.getMetadata` on Tempo that it is an active key of `address`. It stores the key sealed with AES-GCM under a key derived (HKDF) from the `KEY_SECRET` secret, and returns a token `<address>.<64 hex>` that expires with the key. The key's own limit and expiry bound what the cloud can spend. Rotating `KEY_SECRET` makes stored keys and secrets unreadable.
  - `Wallet` (`worker/wallet.ts`) is one Durable Object per account. It holds the key, token digests, secrets, workspaces and one mppx client that ranks challenges as `src/payments.ts` does. All of an account's sessions pay through it, sharing one channel per service; channels live in its synchronous KV storage.
  - `worker/egress.ts` sends the runtime's `api.openai.com` and `api.anthropic.com` requests to `openai.mpp.tempo.xyz` and `anthropic.mpp.tempo.xyz` through the account's `Wallet`. Codex uses HTTPS (`/socket` answers 426), and there are no remote executors (attach a hand).
  - Sessions run in Code Mode without a machine (`codeMode`): each `exec` cell is a Dynamic Worker (the `LOADER` binding), and its `fetch` is `paying` in `worker/env.ts`, which sends every request through the account's `Wallet` and its mppx client, so scripts pay any MPP service from the key; `instructions` lists the services from `src/services.ts`. The `pay` tool is gone.
  - `worker/tools.ts` gives the agent these tools:
    - `http`: unpaid HTTPS, where header values may name secrets as `{{NAME}}`, set with `PUT /v1/secrets/<NAME> {value}`, substituted in the Worker and masked in results;
    - `list_secrets`;
    - a workspace per session that subagents share: `list_files`, `read_file`, `write_file`, `edit_file`, `delete_file`, read over `GET /v1/files[/<session_id>/<path>]`;
    - `wallet`.
  - Checked on 2026-10-22 under `wrangler dev`: with a subagent job running in `/cloud`, the page went to about:blank. When it came back, it reconnected and showed the result, written by both subagents and paid over the OpenAI and rpc proxies. Before that, in a standalone copy, a turn survived `kill -9` of workerd and finished after a restart.
- `npm run deploy` builds and deploys `nanocode-machines-web`, a Worker (`worker/index.ts`, with the `KEY_SECRET` secret) that serves the build through its `ASSETS` binding and relays the device-code requests. Production runs in Cloudflare's Tempo Development Resources account (`CLOUDFLARE_ACCOUNT_ID=0a39052b0a32ba8c8444345fe21b7595`), at https://nanocode-machines-web.tempo-dev.workers.dev. tempoxyz/nanocode-site's Worker serves it at https://nanocode.xyz/machines/ through a service binding with the prefix removed. Vite builds with `base: "./"`, so every URL is relative and the same build works at either address.
