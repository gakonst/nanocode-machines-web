# nanocode-machines-web

A template for a nanocode agent that pays for its own model and tools from the visitor's Tempo Wallet. It is the browser counterpart of gakonst/nanocode-machines, whose `nanocode-mpp` CLI pays per request over MPP sessions, and it serves nanocode.xyz/machines/. It is a Vite and React app: by default the agent, its payments and its wallet connection all run in the visitor's browser, and no server holds keys. Once logged in, the page hands the access key to this site's Worker by default (`/local` opts out and is remembered, `/cloud` opts back in), which runs the same agent durably in a Durable Object, with subagents, and pays from that key while the tab is closed. The Worker also serves the static build and relays Tempo Wallet's device-code requests for logins inside X's player.

- The machine-payments code lives in gakonst/nanocode-ts (see its AGENTS.md): `nanocode-ts/machines` (Tempo Wallet login and key publication, the mppx paying fetch and spend ledger, MCP payment handling, the MPP model catalog, the `/cloud` transport and `createMachine`, the store and transport the pages share), `nanocode-ts/machines/local` (the in-tab agent), `nanocode-ts/machines/react` (`useMachine`, `Spend`, `Meter`, `Prompts`, `SignIn`, `Account`, headless `data-nc` parts) and `nanocode-ts/machines/cloudflare` (`createMachines`: the `Wallet` Durable Object, egress, host tools and the Worker's `/v1`, `/sessions`, `/api/device` and `/api/github` routes). This repository keeps only configuration and skins: `src/machines.ts` (instructions, suggestions and `setup`, which passes the WASM and sqlite loaders to `createMachine`), `src/services.ts`, the pages (`src/App.tsx`, `src/Terminal.tsx`, `src/chatgpt.tsx`, `src/claude.tsx`), the clones' layouts and CSS (`src/clones/`, whose `machineParts` maps the machine parts to their classes) and `worker/index.ts`, which calls `createMachines` with the cloud instructions and re-exports `AgentSession` and `Wallet` under their class names. Paths below that name files that moved refer to nanocode-ts.
- `nanocode-ts/machines/local` runs the nanocode-ts build-d5bbbb2 WASM module (`nanocode-ts`, `nanocode-ts/nanocode_wasm.wasm`) with an in-memory `@sqlite.org/sqlite-wasm` database, as nanocode.xyz's home page does (tempoxyz/nanocode-site `src/demo/Agent.ts`). The session is Codex `gpt-6-luna` at low effort against `https://openai.mpp.tempo.xyz/v1` with subagents enabled, and the SDK's `dispatch` sends each model request through the payment client unchanged.
- `src/machines.ts` holds the instructions and the suggested prompts, and `src/services.ts` the services and request shapes of the nanocode-mpp storm recording (rpc, openrouter, kicksdb, storage, firecrawl, Microsoft and ElevenLabs speech, fal, goflightlabs) plus the Tempo gateway, shared with the Worker's instructions. The agent has no host tools: it runs in Code Mode (`code_mode: true`, whose cells run in the SDK's QuickJS engine inside nanocode-ts's module and whose `fetch` is `nanocode-ts's src/machines/payments.ts`'s mppx fetch, passed as the runtime's `fetch` option), so every `fetch` in an `exec` script pays any MPP service it reaches and the spend panel attributes it per origin. The instructions tell the model to read back only what it needs, because the visitor pays for every token. Before 2026-10-22 its one host tool was `pay`, which reached only `https://<name>.mpp.tempo.xyz`; scripts may now pay any MPP service that allows the page's origin, still bounded by the key's allowance and scopes.
- The agent's gateway entry (`src/services.ts`) lists kv, bucket, metered AI (including the OpenAI-compatible routes) and compute with lease, renew, stream and terminate.
- Both agents, in the tab and in `/cloud`, also have two MCP servers (`servers` in `nanocode-ts's src/machines/mcp.ts`): Mercator (https://mercator.sh/mcp, Tempo's paid API marketplace) and the Tempo gateway (https://gateway.tempo-dev.workers.dev/mcp, kv, bucket, ai and compute as tools). `nanocode-ts/machines/local` passes them as `mcp_servers`, the Worker as nanocode-ts's `createNanocode({ mcp: { servers, fetch } })` with `paying` as `fetch` (gakonst/nanocode-ts's `mcp` option, after build-0d6a500), so the account's `Wallet` pays them in the cloud, and in Code Mode the SDK declares their tools in the `exec` tool's description, so cells call `tools.mcp__gateway__kv_get({...})` or `tools.mcp__mercator__search_services({...})`; `mcp` in `src/services.ts` tells the model so. Every `open` runs `initialize` and `tools/list` on both (free; about 0.8 s from a hosted Hand on 2026-10-23), and a server that fails makes `open` fail, so `nanocode-ts/machines/local` then opens a fresh session without MCP servers. Since nanocode-ts's `deferMcp` (`src/mcp.ts`), the runtime answers `initialize`, `notifications/initialized` and `tools/list` from a per-isolate cache for 10 minutes and fetches the list in parallel with `initialize` on a miss, and lists each tool with only its first sentences and argument names plus a local `describe_tools({ names })` that returns full descriptions and schemas; the two servers' tool list went from 90 KB to 15 KB (2026-10-24), so the `exec` description no longer carries every schema.
  - The SDK sends MCP requests through `dispatch` with their own method, so they go through `nanocode-ts's src/machines/payments.ts`'s mppx fetch. mppx 0.13.6's HTTP transport pays MCP: a paid tool answers HTTP 200 with JSON-RPC -32042 (the gateway's per-call MACH and OUSD session challenges) or with a result whose `_meta` holds `org.paymentauth/payment-required` (Mercator's `create_job`, a one-time charge in USDC.e with `machineTokenEnabled`), and mppx retries the call with the credential in `params._meta["org.paymentauth/credential"]`. It only recognizes those when the request body is a string, so `Mcp.body` decodes MCP bodies, which the SDK hands over as bytes.
  - mppx adds `accept-payment` to every request, and neither server's CORS allows it (in headless Chrome on 2026-10-23 a request with it failed to fetch from both), so `Mcp.crossOrigin` drops it, and `user-agent`, from MCP requests in the tab.
  - Spend is metered per tool: a `tools/call` counts under `<server url>/<tool>`, named by its challenge's description (`gateway · kv.get`, `mercator · Mercator job payment`); a charge counts its credential's challenge amount and a session the rise in `spent` of the receipt in the result's `_meta`. Free calls are not counted. `nanocode-ts's src/machines/cloudflare/wallet.ts` meters the cloud's MCP requests the same way, and decodes their bodies to strings for mppx too.
  - Checked on 2026-10-23 without spending: both servers answered `initialize` and `tools/list` (15 Mercator tools and 26 gateway tools). In Node, nanocode-ts build-0d6a500 opened a Code Mode session with both servers through this dispatch, and a scripted model's `exec` cell called `capabilities`, Mercator's `get_suggested_queries` and `kv_get`: the two free calls returned, and `kv_get`'s -32042 made mppx build a MACH escrow `open` with the 0.05 MACH deposit, which `eth_estimateGas` refused because the throwaway key was not on Tempo. Mercator's `create_job` on a fresh quote made mppx build its charge, a direct USDC.e transfer because the throwaway account held no MACH for the machine-token route, which `eth_estimateGas` refused the same way.
- Tempo's MPP proxies allow browsers. On 2026-10-21 each `*.mpp.tempo.xyz` origin the tool uses answered a preflight from https://nanocode.xyz with `access-control-allow-origin: *`, allowed `authorization`, `content-type`, `payment-session` and `accept-payment`, and exposed `WWW-Authenticate` and `Payment-Receipt`. https://rpc.tempo.xyz allows any origin too. https://mpp.dev/api/services sends no CORS headers, so the service list lives in the instructions.
- `nanocode-ts's src/machines/wallet.ts (nanocode-ts/machines Wallet)` connects Tempo Wallet with the Tempo Accounts SDK (`accounts` 0.21.0, `tempoWallet` with the SDK's default mount, an overlay iframe where the browser supports one and a popup otherwise). The provider is created with `mpp: false`. By default `Provider.create` replaces `globalThis.fetch` with its own mppx client, which pays a 402 by asking Tempo Wallet to sign with the account itself. On 2026-10-21, the first deploy's payment requests went through that polyfill, so Tempo Wallet prompted outside any click and the payments failed as "user rejected the request". `nanocode-ts's src/machines/payments.ts` also keeps the native `fetch` it found at load. The page generates a secp256k1 access key and asks `wallet_connect` to authorize it (`authorizeAccessKey`), as tempoxyz/xframes builds its services keys (`servicesPolicy` and `keyRequest` in its `src/tempo.ts`), with MACH and one fee token:
  - limits of `allowance` (2 MACH) and `feeAllowance` (0.1 USDC.e), and an expiry a day out;
  - scopes for MACH `transferWithMemo`, MACH `approve` to the swapper and the swapper's `swapTo` (machine-token charges), and the TIP-1034 escrow's `open`, `topUp`, `requestClose` and `withdraw`.

A suggestion that spends from the wallet names its budget: on 2026-10-24 gpt-5.6-luna (standing in for GPT-6 Luna, with this page's instructions and the live MCP tool lists) answered "Set every paid service on fire for a minute" 2 of 2 times by asking which services and what budget, and called the services 3 of 3 times when asked to "Call every paid service once in parallel, spending at most $0.05 in total"; asked to search the web with Mercator it quoted and then asked for approval 2 of 2 times, and with "spending at most $0.05" it went on to create_job 2 of 2 times.

  The key, its account and the returned `keyAuthorization` stay in localStorage under `nanocode.machines.wallet` until the key expires or the visitor logs out, so a script on the page could spend at most what is left of the allowance. `restore` drops a stored key without a USDC.e limit, which builds before 2026-10-21's second deploy approved.
- `publish` puts the key on chain before anything pays with it. It sends one transaction that the key signs and that carries its key authorization: the activation call xframes' `activate` sends, MACH `approve(swapper, 0)`, with its fee paid in USDC.e from the visitor's account. That fee counts against the key's USDC.e limit, because Tempo charges an access key's fees to its limit in the fee token.
  - Publishing first is required: the MPP proxies sponsor channel opens, and mppx's fee-payer policy refuses sponsored transactions that carry a key authorization (`allowKeyAuthorization`, off by default). On 2026-10-21 the first paid request with an unpublished key failed with "fee-sponsored transaction keyAuthorization is not allowed".
  - MACH is not a fee token, so the account needs a little USDC.e: that day the RPC quoted the publication's fee as 1,169 atomics (0.001169 USDC.e).
  - Tempo Wallet's MACH checkout opens with `Mach.fund`, and `wallet_revokeAccessKey` revokes the key.
- `nanocode-ts's src/machines/payments.ts` pays with mppx 0.13.6, xframes' version. It ranks challenges as xframes' `payer` does: MACH sessions first, then machine-token charges, then MACH charges. Channels live in localStorage per key, so a reload reuses them.
  - The proxies send no `suggestedDeposit`, so mppx would open each channel with one request's price: on 2026-10-21 the first Luna request's open asked for 289 atomics. Every request therefore passes `context.depositRaw` for a 0.05 MACH opening deposit. Top-ups are also 0.05 MACH, and `maxDeposit` caps a channel at 0.5 MACH.
  - Deposits count against the key's limit. Nothing in the page closes channels.
- `src/Terminal.tsx` is the chat. It guides the visitor through logging in with slash commands, as `nanocode-mpp` asks for `tempo wallet login`, and typing `/` lists them:
  - `/login` approves a key in Tempo Wallet, or reuses an approved one, then publishes it and reports the MACH balance;
  - `/wallet` reads the balances and what the key may still spend;
  - `/fund` opens MACH checkout;
  - `/logout` has this site's Worker delete the key it holds for `/cloud` (`DELETE v1/keys`), then revokes the key in Tempo Wallet and forgets it, and says so when the wallet did not revoke it;
  - `/help` lists the commands.

  Prompts before a login answer with the next step, and payment failures name their fix (`explain` in `src/machines.ts`).

- `nanocode-ts/machines/react` is the spend panel of the nanocode-mpp TUI. Its title reads `⚡ <total> MACH streamed · <n> paid calls · <n> services · <rate> MACH/min`. Each service has a row with a live `●`, a 30-second sparkline, its spend and its call count. `payments.ts` takes spend from receipts:
  - session receipts come from `Payment-Receipt` headers and from the `payment-receipt` events of metered streams, which it reads as the stream passes through unchanged. Each is charged as the rise in its channel's cumulative `spent` since the last receipt this browser saw, which is kept in localStorage;
  - charges are taken from their challenge's amount on mppx's `payment.response` event.

- `/cloud` runs the agent durably in this site's Worker instead of the tab (`worker/`). The page sends its access key to `POST v1/keys`, and from then on its turns go to `sessions/<session>/turns` and it follows `sessions/<session>/events` (`nanocode-ts's src/machines/cloud.ts`). A turn keeps running when the tab closes. The page keeps its transcript in localStorage (`nanocode.machines.entries`, the last 300 entries), so a reload shows the conversation and reconnects to an open turn from its saved cursor. In `/cloud` a running turn locks nothing: New chat, switching chats, deleting chats and the suggestions stay enabled (a suggestion or prompt sent while a turn runs steers it); leaving a conversation aborts the transport's signal, so `nanocode-ts's src/machines/cloud.ts` stops reading that session's stream and leaves the turn running in the cloud without touching the session the next conversation restores, and coming back resumes it from the conversation's saved cursor. In this tab the transport has no `resume`, so New chat and switching wait for the turn. `/clear` starts a new session. In the cloud the spend panel is the same `Spend`, fed by `Cloud.meter`, which polls `v1/me` every second for the `Wallet`'s spend (from receipts) and request counts per service and operation and turns each rise into a charge for the sparkline. The proxies share one session channel across services and lower a channel's `spent` when a request costs less than its estimate, so each receipt's change from the channel's previous receipt, up or down, goes to the route that received it (a running high-water mark hid every later request's cost under the first estimate). Rows are named by the MPP challenge's `description`, which the `Wallet` and `nanocode-ts's src/machines/payments.ts` keep per route (origin and path) from each 402's `WWW-Authenticate` and each payment's challenge: `gateway · kv.set`, `openai · gpt-6-luna - generation`, `rpc · JSON-RPC calls - $0.001 per call (1)`. A route that has not answered a 402 yet shows as its host. Checked on 2026-10-22 under `wrangler dev`: one turn's paid calls to rpc, gateway `kv/set` and `kv/get` showed as separate rows. `/local` goes back to the tab, and `/logout` also forgets the cloud token. The Worker is gakonst/nanocode-cloudflare-durable's `createNanocode` (sessions in Durable Objects, durable turns, `subagents: true`, hands), pinned by commit:
  - `POST /v1/keys {address, key_type: secp256k1 | p256, private_key}` derives the key's address and checks with `accessKey.getMetadata` on Tempo that it is an active key of `address`. It stores the key sealed with AES-GCM under a key derived (HKDF) from the `KEY_SECRET` secret, and returns a token `<address>.<64 hex>` that expires with the key. The key's own limit and expiry bound what the cloud can spend. Rotating `KEY_SECRET` makes stored keys and secrets unreadable.
  - `Wallet` (`nanocode-ts's src/machines/cloudflare/wallet.ts`) is one Durable Object per account. It holds the key, token digests, secrets, workspaces and one mppx client that ranks challenges as `nanocode-ts's src/machines/payments.ts` does. All of an account's sessions pay through it, sharing one channel per service; channels live in its synchronous KV storage.
  - `nanocode-ts's src/machines/cloudflare/egress.ts` sends the runtime's `api.openai.com` and `api.anthropic.com` requests to `openai.mpp.tempo.xyz` and `anthropic.mpp.tempo.xyz` through the account's `Wallet`. Codex uses HTTPS (`/socket` answers 426), and there are no remote executors (attach a hand).
  - Sessions run in Code Mode without a machine (`codeMode`): each `exec` cell runs in the SDK's QuickJS engine, compiled into nanocode-ts's module, inside the session's Durable Object, and its `fetch` is `paying` in `nanocode-ts's src/machines/cloudflare/env.ts`, which sends every request through the account's `Wallet` and its mppx client, so scripts pay any MPP service from the key; `instructions` lists the services from `src/services.ts`. The `pay` tool is gone. Redeployed with QuickJS cells (nanocode-ts build-ce9f311, nanocode-cloudflare-durable 9a331e6), the same cloud turn's cell paid both requests in 1.4 s and the turn took 11.2 s.
  - `nanocode-ts's src/machines/cloudflare/tools.ts` gives the agent these tools:
    - `http`: unpaid HTTPS, where header values may name secrets as `{{NAME}}`, set with `PUT /v1/secrets/<NAME> {value}`, substituted in the Worker and masked in results;
    - `list_secrets`;
    - a workspace per session that subagents share: `list_files`, `read_file`, `write_file`, `edit_file`, `delete_file`, read over `GET /v1/files[/<session_id>/<path>]`;
    - `wallet`.
  - Checked on 2026-10-22 under `wrangler dev`: with a subagent job running in `/cloud`, the page went to about:blank. When it came back, it reconnected and showed the result, written by both subagents and paid over the OpenAI and rpc proxies. In the browser, an init script that sends https://rpc.tempo.xyz requests to the stub and seeds `nanocode.machines.wallet` logs the page in. On 2026-10-24 that way, Luna and Haiku turns opened a channel, topped it up and paid models, gateway kv, bucket and compute tools (direct and through `call_tool`) and Mercator search, and `/v1/me` and the clones' meters matched the shims' ledger to the unit; `/logout` made the Worker answer 401 for the token, and an expired key's token answered 401.
- Develop with `npm install` and `npm run dev`, and check with `npm run check` and `npm run build`. Do not add code comments, README files or tests. Keep logs and other artifacts in ignored `output/`.

- nanocode-ts is pinned to a commit (`"nanocode-ts": "github:gakonst/nanocode-ts#<full sha>"`), not a release tarball. Move it with `npm install github:gakonst/nanocode-ts#<full sha>` right after the nanocode-ts change lands: its prepare script fetches the prebuilt WASM for that commit's fingerprint and builds only the TypeScript, so there is no release to wait for.

Web search uses each harness's upstream tool, paid over MPP like the models: Claude's `WebSearch` sends a nested Messages request with Anthropic's `web_search_20250305` to anthropic.mpp.tempo.xyz, billed by the token on the session, and Codex's `web__run` posts to openai.mpp.tempo.xyz's `/v1/alpha/search`, a one-time $0.01 MPP charge per call ("Standalone web search" in the spend panel). Both proxies answer CORS preflights from any origin, so the tab pays them directly, and the Worker's egress maps them like model requests. They need nanocode-ts 8245713 or later. `Services.search` tells both agents to call the tool from an exec script, since Code Mode refuses top-level calls, and to prefer it to Mercator for plain web search. On 2026-10-24 a local `wrangler dev` of the Worker with a registered access key answered "search the web for today's Tempo blockchain news and cite 2 links" with live results on Luna (one $0.01 standalone search) and on Haiku 5.5 (four `WebSearch` calls in cells, paid through anthropic.mpp.tempo.xyz).
